# 人工测试清单

迁移完成后、合并到 `staging` 之前需要人工执行的测试。分三部分：后端、前端、端到端。

架构说明见 [`architecture.md`](architecture.md)，接口细节见 [`api-contract.md`](api-contract.md)。

## 0. 说明

**自动化已经覆盖、不需要人工重复的部分**

| 范围 | 由谁覆盖 |
|---|---|
| 接口的信封、状态码、错误字符串、口令保护、已删除的旧接口 | 后端 `test/api-contract.e2e-spec.ts`（假抓取器） |
| 跨域默认关闭与显式开启 | 后端 `test/cors.e2e-spec.ts` |
| 各服务的分支逻辑（队列去重与恢复、章节名改写、查重、库文件读写等） | 后端单测 |
| store、接口层、各组件的状态与分支 | 前端单测 |
| 搜索 → 添加 → 删除（含口令）的界面流程 | Playwright 冒烟用例（假抓取器） |
| 镜像能构建、抓取模块能导入 | CI |

**自动化覆盖不到、所以要人工测的部分**：真实源站、真实 Kavita、真实 FlareSolverr、真实容器、旧数据升级、长时间运行、真实浏览器里的观感。

**准备**

- [ ] 用现有 `manga_library.json`、封面目录和下载目录的**副本**，不要直接用生产数据
- [ ] 构建镜像：`docker build -t vanmanga .`
- [ ] 准备两套配置各跑一遍关键项：不设 `ADMIN_TOKEN`、设了 `ADMIN_TOKEN`
- [ ] 记录测试用的 Node、Docker、浏览器版本

## 1. 后端

用 `curl`、Swagger（`/api/docs`）或日志验证，不依赖前端界面。

### 1.1 启动与配置

- [ ] 容器启动后 `GET /api/config` 返回 200，健康检查变为 healthy
- [ ] 日志里没有未处理的异常；启动扫描的日志出现并正常结束
- [ ] 把某个数值型变量写错（如 `PORT=abc`）：进程拒绝启动，报错里点出变量名
- [ ] 只设旧变量 `LIB_PATH`、不设 `LIBRARY_FILE`：启动日志有明确告警
- [ ] 不设 `KAVITA_*`：`GET /api/config` 的 `kavitaEnabled` 为 `false`
- [ ] 设了 `ADMIN_TOKEN`：`adminRequired` 为 `true`；不设为 `false`
- [ ] 容器以非 root 用户运行；挂载目录的权限足够写入库文件、封面、下载目录

### 1.2 旧数据兼容（从 Flask 版升级）

- [ ] 用 Flask 版的 `manga_library.json` 副本启动：`GET /api/library` 的数量与原来一致
- [ ] 旧记录的封面能通过 `GET /api/library/<id>/thumbnail` 取到（旧记录里存的是带域名的地址）
- [ ] 没有 `updated_at` 的旧记录不报错，排序时按 `add_date` 处理
- [ ] 启动后库文件内容没有被无故改写（对比启动前后的文件）
- [ ] 把库文件副本改坏（删掉结尾的 `}`）后启动：进程报错退出，文件内容未变
- [ ] 恢复文件后启动正常，数量一致
- [ ] 库文件不存在时启动：自动创建空库

### 1.3 搜索与添加（真实源站）

- [ ] `GET /api/scraper/dgmanga/search?q=<真实漫画名>` 返回候选，封面地址可访问
- [ ] 搜不到的词返回空数组而不是错误
- [ ] `q` 为空返回 400 `query-required`
- [ ] `POST /api/library` 添加一部：返回 200，库文件里出现记录，封面文件落盘，下载任务自动入队
- [ ] 重复添加同一部：409 `already-in-library`
- [ ] 添加名字相近的另一部：409 `duplicate` 并列出相近标题；带 `submit_sign: '1'` 重发后成功
- [ ] 等搜索缓存过期（或重启后端）再添加：410 `search-expired`
- [ ] 添加 id 以 `-` 开头的漫画：抓取子进程不把它当成命令行选项

### 1.4 下载与命名（真实源站）

- [ ] 整部下载：每章生成一个 zip，路径为 `<下载目录>/<名字>$<id>/<名字>/<章节>.zip`
- [ ] 对一部用 Flask 下载过的连载漫画触发更新：新章节的压缩包名与旧章节风格一致（如 `第68-第69话`、`v$2`），目录里没有同一话的两种命名
- [ ] 库里 `last_epi_name` 与最新压缩包名一致，`last_epi` 等于已下载章节数
- [ ] 名字带 `/` 的漫画：目录是 `名字-带横线$id` 单层目录，没有嵌套
- [ ] 重下某一话（`POST /api/download/chapters`）：压缩包被覆盖而不是多出一份
- [ ] 下载中断网几分钟：失败图片过多的章节不产生压缩包，也不留半成品目录，`last_epi` 不前进；下次扫描会重试
- [ ] 一张图都没下到（如源站封锁）：记录不被标成已完成
- [ ] 大批量下载时看日志：章节页遇到 429 会等待后重试，而不是跳过该章
- [ ] 下载完成后 `updated_at` 更新；对已是最新的漫画再跑一次，`updated_at` 不变
- [ ] `NUMBER_OF_WORKERS`、`IMAGE_CONCURRENCY`、`IMAGE_DELAY_MS` 调整后行为随之变化，且不被源站封

### 1.5 队列与重启恢复

- [ ] 连续添加三部：`GET /api/download/queue` 显示一个进行中、两个等待，按添加顺序执行
- [ ] 同一部漫画重复提交整部下载：不产生第二个任务
- [ ] 对同一部漫画两次提交不同章节的重下：等待中的任务合并章节
- [ ] 下载进行中重启容器：重启后队列恢复，被打断的任务从已下载的章节之后继续，不重下已完成的章节
- [ ] 把 `queue.json` 改成非法内容后启动：进程正常启动，坏文件被改名留存，队列为空
- [ ] 手动往 `queue.json` 里放一个库里不存在的漫画的任务后启动：该任务运行时被跳过，不重建目录，后面的任务照常执行

### 1.6 删除与保护

- [ ] 不设 `ADMIN_TOKEN`：`DELETE /api/library/<id>` 直接成功
- [ ] 设了 `ADMIN_TOKEN`：不带请求头 401 `admin-token-required`；带错的 401 `admin-token-invalid`；带对的成功
- [ ] `POST /api/library/rezip` 同样受保护
- [ ] 删除成功后：库记录、下载目录、封面文件都被清掉
- [ ] 删除正在下载或排队中的漫画：409 `manga-busy`，什么都没删
- [ ] 删除不存在的 id：404 `manga-not-found`
- [ ] 重新打包：下载目录里残留的章节文件夹被打成 zip，已有的 zip 不受影响

### 1.7 定时任务

- [ ] 启动扫描：首次下载没完成的漫画一律入队；已下完且自动更新关闭（`download_switch` 为 1）的被跳过；其余的只有在源站章节数多于 `last_epi` 时才入队
- [ ] 首次下载没完成的漫画即使关了自动更新也会被入队（既有行为，确认是否符合预期）
- [ ] 启动扫描期间删除一部漫画：扫描继续，进程不退出
- [ ] 01:30 的每日扫描按时触发（可临时改容器时间，或等一晚看日志）
- [ ] 连续运行 24 小时以上：内存没有持续增长，日志里没有重复报错

### 1.8 Kavita（需要真实 Kavita）

- [ ] 配好三个 `KAVITA_*` 变量后启动：日志显示同步成功，库里 `kavita_url` 被填上
- [ ] Kavita 不可达时启动：后端照常启动，不被卡住
- [ ] `POST /api/kavita/login` 用正确账号返回登录链接；错误账号 403 `kavita-login-failed`；Kavita 停掉时 502 `kavita-unreachable`，响应里不含内部地址
- [ ] 整部下载完成后，Kavita 里出现或更新了对应系列
- [ ] 重下一话后同样触发了 Kavita 扫描
- [ ] 名字带 `/` 的漫画下载后 Kavita 能扫到
- [ ] 每 6 小时的同步按时触发（看日志）

### 1.9 Cloudflare（需要 FlareSolverr）

- [ ] 配了 FlareSolverr、源站无验证时启动：日志为 `CF protection inactive`，没有调用 FlareSolverr，也没有注册 12 分钟复查
- [ ] 源站开启验证时：日志为 `CF challenge detected, solving...`，之后抓取正常
- [ ] 验证消失后：复查任务被注销
- [ ] 不配 FlareSolverr：相关逻辑整体跳过，不报错

### 1.10 下架（DMCA）

- [ ] 源站把某部漫画下架后触发它的下载或扫描：漫画从库里移除，下载目录被删除，推送 `dmca_alert`（这是既有行为，确认是否符合预期）

### 1.11 安全

- [ ] 不设 `CORS_ORIGINS`：从另一个域名的网页用 `fetch` 调 `POST /api/library` 或 `DELETE` 被浏览器拦下
- [ ] 设了 `CORS_ORIGINS=https://a.example`：该来源放行，其他来源仍被拦
- [ ] 请求体超过 1 MB：413 `payload-too-large`
- [ ] `GET /api/library/..%2F..%2Fetc%2Fpasswd/thumbnail` 之类的路径：返回 404，不泄露文件
- [ ] 任何 5xx 响应里都不含堆栈、文件路径、内部主机名
- [ ] 日志里不出现管理口令、Kavita API Key、Kavita 密码

## 3. 端到端

用真实镜像、真实源站、真实外部服务，把后端和前端串起来走完整场景。每个场景同时核对三处：界面、接口返回、磁盘上的文件。

### 3.1 全新部署

- [ ] 按 README 的 `docker run` 示例启动，空数据目录
- [ ] 打开页面 → 搜索一部短篇漫画 → 添加 → 队列出现任务 → 进度实时推进 → 完成提示
- [ ] 下载目录里的 zip 数量等于章节数；随机解压两个确认图片完整、顺序正确
- [ ] 卡片显示最新章节和"刚刚"

### 3.2 从 Flask 版升级

- [ ] 按 README 的升级步骤操作，使用旧数据的副本（包括 `LIB_PATH` → `LIBRARY_FILE` 这一步）
- [ ] 启动后界面里漫画数量、封面、最新章节与旧版一致
- [ ] 启动扫描只把确实有新章节的连载漫画入队，没有把整个库重下一遍
- [ ] 新下载的章节与旧章节在同一目录、命名风格一致
- [ ] 旧版的浏览器书签（`/mainpage/...`）仍能打开

### 3.3 日常更新

- [ ] 保持容器运行过夜：01:30 的扫描把有更新的连载漫画入队并下载完成
- [ ] 第二天打开页面：有更新的漫画排在最前并带"新"
- [ ] 关闭某部已下完漫画的自动更新后，它不再被扫描下载；重新打开后恢复

### 3.4 重下与重新打包

- [ ] 手动删掉某一话的 zip → 界面里选该章节重下 → zip 重新出现
- [ ] 在下载目录里手动放一个未打包的章节文件夹 → 设置页点重新打包 → 文件夹变成 zip
- [ ] 两项操作完成后 Kavita 都能看到变化

### 3.5 删除

- [ ] 设了口令的环境里：界面删除一部漫画，走完确认和口令 → 卡片消失 → 库文件、下载目录、封面都没有它了 → Kavita 下次扫描后系列消失或变空
- [ ] 删除一部正在下载的漫画：界面上按钮禁用；用 `curl` 强行调用得到 409

### 3.6 中断与恢复

- [ ] 下载到一半 `docker restart`：页面先显示断线提示，容器起来后自动恢复，队列还在，下载从断点继续，最终章节齐全且没有重复
- [ ] 下载到一半拔网线几分钟再恢复：任务最终完成或在下次扫描时补齐，没有残缺的 zip
- [ ] 下载到一半 `docker kill`（非正常退出）后启动：库文件和队列文件都能正常读取
